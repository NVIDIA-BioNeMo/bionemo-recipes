    Runnable modality examples

    Example Raw inputs Encoder Stages
    Genetics Eight short synthetic DNA sequences Evo2-1B, layer 12 Alignment, full decoder SFT, LoRA or full decoder GRPO
    Chemistry Eight simple SMILES strings NV-KERMT-70M-v2 Alignment, full decoder SFT, LoRA or full decoder GRPO
    LLaVA Images CLIP Alignment, LoRA SFT, GRPO, inference

    Genetics and chemistry share a chat-style JSONL input: sample_id, messages, and answer. Messages can interleave text blocks with encoder inputs: {"type": "dna", "sequence": "ACGT"} or {"type": "molecule", "smiles": "CC"}. Each block places its soft tokens among the text; the raw sequence or SMILES is consumed by the encoder. The example READMEs show complete two-input records. Like HF multimodal chat, the list order is the prompt order. These custom modalities are encoded by the demo preparation scripts, which retain typed messages alongside cached features. Chemistry blocks also carry canonical graph geometry; DNA span lengths come from the sequence and the configured Evo2 pooling window. The examples define explicit KERMTProcessor and Evo2Processor classes that wrap the base checkpoint processor loaded by AutoProcessor. They format only their molecule or dna blocks in apply_chat_template and delegate native processing to that base instance. Images and other native blocks pass through unchanged. Histories preserve system/user/assistant roles, plain text content, and text-only turns or records. answer is the ground-truth value used for scoring; the default training response is \boxed{...}. Optional target supplies a different completion, reasoning_content supplies the native assistant reasoning field, and chat_template_kwargs selects per-record rendering. The bundled first and last records demonstrate reasoning; the remaining records use direct answers. No custom chat-template engine is needed.

    Genetics and chemistry include their raw JSONL inputs, endpoint clients, model wiring, and production-based training configs. Their count questions exercise the training path; the same eight records are used in every stage. Training defaults now follow the production recipes; use bounded step/data overrides for sanity checks. The bundled records are not evaluation datasets.

    Keep genetics and chemistry application Python within a combined budget of 600 nonblank lines, excluding tests. Use package and upstream APIs for training, configuration, artifacts, and transport.

    Build the training environment

    The single Dockerfile builds one image for LLaVA, genetics, and chemistry. It installs Stitch, all three example plugins, pytest, RDKit, and the typed BioNeMo perception client into the pinned NeMo framework interpreters. It does not reinstall training frameworks. The default base uses BioNeMo's public mirror. From the BioNeMo recipes/nemotron-stitch directory:

    git clone https://github.com/NVIDIA-dev/bionemo-perception-containers.git ../bionemo-perception-containers
git -C ../bionemo-perception-containers checkout aa831c731f30e9f7bb878e9e29c0e61848f36e1d
docker build -f examples/Dockerfile \
  --build-context perception=../bionemo-perception-containers \
  -t stitch-examples .

    Select an example with -w /opt/stitch/examples/llava, -w /opt/stitch/examples/genetics, or -w /opt/stitch/examples/chemistry when running the image. LLaVA uses local CLIP; genetics and chemistry use encoder services. The optional super build target selects Transformers 5.18 in every worker and requires a compatible AutoModel base supplied through BASE_IMAGE. The image applies no framework source patches.

    The perception repository supplies the client and encoder services; no other application repository or prebuilt dataset is needed. For an existing compatible NeMo environment, install this package and the selected example with --no-deps, install ../bionemo-perception-containers/clients/python[numpy], and put the selected example directory on PYTHONPATH.

    Connect to the encoders

    Set the base URL or full /v1/forward URL for the selected service:

    export EVO2_URL=http://127.0.0.1:8000
export KERMT_URL=http://127.0.0.1:8003
# Optional for authenticated endpoints; omit for local open services:
# export EVO2_TOKEN=...
# export KERMT_TOKEN=...

    The client sends tokens as bearer authorization headers. Tokens and endpoint URLs are not written into feature manifests or caches. Preparation fails on HTTP errors, invalid checksums, wrong layers/pooling, nonfinite features, or incompatible geometry. It never substitutes random features.

    Local services require GPUs, their model weights, and the perception images. Build and launch instructions are in the upstream Evo2 service and KERMT service documentation. Both can run on the same machine as the training container. The local genetics service below uses the 1B profile, exposing decoder.layers.12 with 1,920-wide features and window-64 mean pooling, on one GPU. Set the gene YAML projector widths to 1920 for that service; the shipped defaults use the production Evo2-20B width of 8192. KERMT must expose unpooled molecule, atom, and both bond branches. Example local launch commands, after provisioning those images and weights:

    # Build the current /v1/forward server; EVO2_CACHE_DIR supplies its populated 1B NIM cache.
docker build -f ../bionemo-perception-containers/models/evo2/Dockerfile \
  -t bionemo-perception-evo2:local ../bionemo-perception-containers
docker run --rm --gpus '"device=0"' --shm-size=16g -p 127.0.0.1:8000:8000 \
  -v "$EVO2_CACHE_DIR:/opt/nim/.cache:ro" \
  -v "$PWD/../bionemo-perception-containers/packaging/nimcraft/evo2.model_manifest.yaml:/manifest.yaml:ro" \
  -e NIM_MANIFEST_PATH=/manifest.yaml -e NIM_DISABLE_MODEL_DOWNLOAD=true \
  -e NIM_CACHE_PATH=/opt/nim/.cache -e EVO2_MODEL_ID=evo2-1b-8k \
  -e EVO2_EMBEDDINGS_LAYER=decoder.layers.12 bionemo-perception-evo2:local

# In another terminal. KERMT_WEIGHTS_ROOT must contain the converted safetensors checkpoint.
# KERMT_IMAGE defaults to bionemo-perception-kermt:local, built from its upstream Dockerfile.
KERMT_WEIGHTS_ROOT=/absolute/path/to/kermt-weights \
  docker compose -f ../bionemo-perception-containers/models/kermt/compose.yaml up

    Stop encoder services after cache preparation to free their GPUs for training.

    Prepare and train

    Select one example, then open its training shell. Linux host networking lets this container reach services listening on the host's loopback interface:

    example=genetics  # or chemistry
mkdir -p "examples/$example/artifacts" "examples/$example/outputs"
docker run --rm -it --gpus all --ipc=host --network host --cap-add SYS_PTRACE \
  -e EVO2_URL -e EVO2_TOKEN -e KERMT_URL -e KERMT_TOKEN \
  -v "$PWD/examples/$example/artifacts:/opt/stitch/examples/$example/artifacts" \
  -v "$PWD/examples/$example/outputs:/opt/stitch/examples/$example/outputs" \
  -w "/opt/stitch/examples/$example" stitch-examples

    Inside the selected example directory, prepare the cache and download the base model:

    python prepare.py
hf download nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-BF16 \
  --revision b3caaabed0263651a17dc1f2d4ce97e794f76c44 \
  --local-dir artifacts/models/lightning-30b-bf16

    Both preparation scripts accept optional --encoder-model MODEL_ID and --encoder-revision REVISION flags. These record your declared encoder identity in the manifest header and cache contract, so different declarations produce different cache identities. Omitted values stay unknown (empty strings) and preparation continues. These settings record metadata; they do not select or verify the model running at the endpoint.

    Preparation makes eight requests, one per raw input, then publishes one manifest with 24 stage-tagged records and separate manifest-{stage}-train.jsonl files. Every cached tensor is checksummed. Generated data lives in artifacts/data/; model weights, caches, and outputs/ are ignored by Git. For another preparation run, use python prepare.py --output artifacts/data-new and update config paths, or remove the generated artifacts/data/ first. Published caches are immutable. Regenerate older prepared data for either demo: manifests now retain typed content blocks with cached geometry; chemistry also groups cached features by branch across all inputs and records molecule_count. --input accepts another JSONL in the same format.

    Training settings follow the selected production recipes in nemotron-stitch-demos: indexed full-parameter chemistry, flanked-v3 shuffled full-parameter Lightning SFT, and paired public Super. Alignment trains projectors; SFT trains the decoder and projectors, including native boundary embeddings. All alignment/SFT configs use THD packing, one pack per microbatch. Both examples instantiate PackedManifestFeatureDataset directly, with the native packed collator and processor configuration. Chemistry supplies its three-projector ChemistryCollator through the upstream collator loader.

    Recipe Global batch Updates Warmup Peak LR Pack tokens
    Chemistry alignment 8 packs 705 21 3e-3 16,384
    Chemistry full SFT 8 packs 1,410 42 1e-5 16,384
    Gene Lightning/Super alignment 16 packs 2,000 60 3e-3 4,096
    Gene Lightning full SFT 16 packs 5,000 250 1e-5 4,096
    Gene paired Super full SFT 16 packs 4,945 248 1e-5 4,096

    The gene SFT source runs used padded samples; these examples deliberately use THD packs in both supervised stages. The per-update token exposure changes; this is a recipe with production optimization settings, not bit-exact replay. Gene YAMLs directly configure the production Evo2-20B feature width (8192) and pooling window (64). Preparation reads those same values with python prepare.py --config configs/alignment.yaml; no encoder environment variables are needed. For a local Evo2-1B endpoint set the stage YAML projector input widths to 1920. Use a matching/new cache when changing encoder settings; span lengths are derived by the processor and are not dataset fields. The Dockerfile pins the production fused cross-entropy implementation. Each config cites its source recipe; loss reduction, precision, scheduler, and distributed settings come from that source. Launch topology lives in the application, including the paired Super multinode launch. There is no single-node memory-tuning overlay.

    The eight short rows pack into fewer than eight training samples. The pinned AutoModel distributed sampler drops incomplete rank groups, so the original manifest gives empty loaders on eight ranks; more epochs cannot repair this. For a bounded sanity run, write a separate repeated view of the prepared manifest. Unique sample IDs reuse the same checksummed feature keys, so this makes no additional encoder requests and leaves the published cache intact. These repeated exposures have no interpretation as additional training data.

    import json
from pathlib import Path

source = Path("artifacts/data/manifest.jsonl")
rows = [json.loads(line) for line in source.read_text().splitlines()]
repeated = [
    {**row, "sample_id": f"{row['sample_id']}-sanity-{copy}"}
    for copy in range(256)
    for row in rows
]
source.with_name("manifest-sanity.jsonl").write_text(
    "".join(json.dumps(row) + "\n" for row in repeated)
)

    Run both stages with the repeated view and explicit three-update bounds:

    for stage in alignment sft; do
  torchrun --nproc-per-node 8 -m nemo_automodel.cli.app "configs/$stage.yaml" \
    --dataset.manifest_path=artifacts/data/manifest-sanity.jsonl \
    --step_scheduler.max_steps=3 --step_scheduler.num_epochs=1000 \
    --step_scheduler.ckpt_every_steps=3 --step_scheduler.save_checkpoint_every_epoch=false
done

    Keep the -- prefix on every AutoModel override: the pinned parser silently ignores bare key=value arguments. After changing raw data, tokenizer, pack budget, or rank count, verify that each distributed loader has at least one optimizer update's worth of microbatches; the repeated view is tested at the loader boundary only for the bundled records and documented eight-rank settings. This does not qualify end-to-end training or model quality.

    Production dataset conversion, stage/split selection, cache publication, qualification launchers, and run receipts belong in the demos repository. A bounded qualification keeps these example configs and model code, changes the data/model/output paths, and stops early; it preserves the full LR schedule, batch sizes, packing, and production node topology. Do not use the tiny bundled preparation script as an in-memory encoder pipeline for a million-row corpus.

    Alignment exports outputs/alignment/projector/. SFT loads that artifact and writes outputs/sft/projector/, outputs/sft/trainability.json, and decoder checkpoints under outputs/sft/checkpoints/.

    GRPO

    GRPO freezes the SFT projectors. Chemistry defaults to the indexed full-decoder recipe on two eight-H100 nodes: 24 prompts × eight responses, LR 1e-6, KL 0.01, 1,024 new tokens, and vLLM TP2/EP2. Gene defaults to a fresh rank-128 LoRA on the consolidated full-SFT decoder, using the reference four-node settings: 256 prompts × eight responses, LR 1e-6 with three-update warmup, KL 1e-4, 512 new tokens, policy EP8/DP4, and generation EP8. grpo-full.yaml disables LoRA for gene; for chemistry it is an alias of the default full-decoder recipe. Super uses the same gene GRPO settings with native Super model wiring; its end-to-end GRPO qualification remains pending.

    python -m nemotron_stitch.nemo_rl.runner --config configs/grpo.yaml

    Set STITCH_SFT_MODEL to select another consolidated SFT decoder. Both examples use NeMo RL's built-in geo3k boxed-answer verifier with format_score: 0.0: only final-answer correctness contributes reward. An MC record supplies its option letter as answer, and the model emits \boxed{A}. No reasoning, formatting, or semantic reward bonus is added. This also scores the bundled integer-count questions. Explicit production target/reasoning fields remain unchanged. Policy sequence packing stays disabled, matching the selected GRPO recipes; THD packing applies to alignment and SFT.

    The eight-row data cannot supply the production rollout batch. For a bounded sanity GRPO run, override the prompt count, global batch, duration, and epoch limit explicitly. Qualification on production data keeps the production batch and node topology. Use the native NeMo RL/Ray multinode launch rather than launching these configs on only the local eight GPUs.
